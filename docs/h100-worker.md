# H100 x86 worker deployment

The 2026-11-12 user decision accepts H100 amd64 and Vista ARM64 results as equivalent without cross-architecture validation. Preserve task versions, images registered for each architecture, BF16 checkpoint, 131072-token context, thinking, sampling, native budgets, one concurrent attempt and all 4 assigned slots. Measurements and trajectories are never training data.

## Install

Use an x86_64 compute host with Apptainer 1.4+, Python 3.13 for Harbor, Python 3.12 for inference, an NVIDIA driver compatible with CUDA 12.8 wheels, and sufficient local storage. A practical host reservation is at least 128 GiB RAM and one exclusively assigned H100 80 GB. This runner requires Slurm; it is not a bare-metal process scheduler. CUDA compiler paths and Slurm allocation/partition/GRES are local settings, not Vista requirements. The amd64 example requests exactly one GPU with `slurm_gres="gpu:1"`; set the local GPU type if required.

Install the base/patched Harbor runtime using the README command, then apply the separately versioned x64 manifest compatibility edit to that **new local runtime**:

```bash
runtime_python="$SCRATCH/dbt-bench-runtime/timeout-v2/venv/bin/python"
"$runtime_python" scripts/apply_platform_runtime.py --platform linux-amd64
UV_PROJECT_ENVIRONMENT="$SCRATCH/dbt-bench-inference-x64" \
  uv sync --locked --project inference/x86_64 --python 3.12
"$runtime_python" scripts/build_qwen_platform.py \
  --cache "$SCRATCH/dbt-bench-cache/qwen-x64" \
  --output "$SCRATCH/dbt-bench-qwen-x64"
cp configs/local.amd64.example.toml configs/local.toml
export DBT_BENCH_LOCAL_CONFIG="$PWD/configs/local.toml"
```

Use Python 3.13 for the bundle builder (tar extraction filters are required). Fill local paths, allocation and partition. Set `qwen_bundle` to the generated `bundle.json` and `vllm_executable` to the x64 environment. The builder downloads only Node/NVM and npm tarballs at locked URLs, verifies their hashes/integrities, and checks the full canonical archive/inventory against `runtime/qwen-code/linux-x64/bundle.lock.json`. It does not execute a foreign binary. The native Harbor adapter runs the x64 installer's host guard and Node/npm/Qwen version checks before an attempt starts. The original ARM receipt and adapter inventory remain separate.

The x64 lock contains vLLM 0.19.0, Torch 2.10.0+cu128, torchaudio 2.10.0+cu128 and torchvision 0.25.0+cu128. Every dependency shared with the original ARM inference lock has the same version. The x64 vLLM wheel SHA256 is `2d0e5fae45367bdbf111fcad68f4c0f8fdddd2f2fb643e52f0f2daebef7b41cf`. `uv sync --locked` verifies artifact hashes. Do not run `uv lock --upgrade` for measurement deployments.

## Memory and startup

Start with the unchanged protocol command generated by the runner: BF16, `--max-model-len 131072`, `--max-num-seqs 1`, `--gpu-memory-utilization 0.90`, language model only, the fixed parsers and seed. Tensor parallelism defaults to 1. Use one GPU visible to the job. Load the model once per batch. The runner records the full server command and actual Python/vLLM/Torch versions. CPU count, RAM, compiler and paths remain deployment settings.

The locked checkpoint files total about 66.97 GiB on disk, including components the language-only service may not load. Its text config has 10 full-attention layers, 2 KV heads and head dimension 256; BF16 full-attention KV for 131072 tokens alone is 2.5 GiB. Linear-attention state, kernels, activations, CUDA graphs and allocator overhead add to that. These are sizing estimates, not a GPU startup test or guarantee that the 0.90 allocation fits on every H100. See the [fixed model config](https://huggingface.co/Qwen/Qwen3.6-35B-A3B/blob/995ad96eacd98c81ed38be0c5b274b04031597b0/config.json) and [vLLM 0.19 cache settings](https://github.com/vllm-project/vllm/blob/v0.19.0/vllm/config/cache.py).

This release deliberately keeps the existing server arguments intact. Do not reduce context, switch to FP8 weights/KV, increase concurrency or alter native attempt budgets to fit memory. If the unchanged startup fails for memory, keep the startup logs and request a recorded deployment adjustment before measurement. Weight CPU offload can retain precision but may slow each forward pass on PCIe H100; it is a possible separately recorded fallback, not a default silently added here ([vLLM 0.19 offload implementation](https://github.com/vllm-project/vllm/blob/v0.19.0/vllm/config/offload.py)).

## Ready gate

The x64 lock and bundle assembly were CPU checked on ARM. No H100 inference service, amd64 CLI, Docker build or amd64 reference execution was run during this change. The owner builds/publishes images, fills `images/platform-images.json`, and runs `scripts/smoke_image.py` on amd64. Then workers follow the unchanged ledger claim/check loop and README preparation/export commands. Local failures are preserved and returned to the owner; workers never rerun slots themselves.
